# Интерактивная установка и пробная загрузка ядра

Предварительный мастер **1.0.0-rc1** использует неизменённый проверенный комплект
**v1.7.11-dsg2-rc3**. Он автоматизирует работу с GRUB и сохраняет этап между
перезагрузками. Проверки модуля, сети, происхождения пакетов и ограничения
переустановки остаются в rc3.

В SSH-консоли под root:

```bash
curl -fsSL https://raw.githubusercontent.com/ialexisizotov-ctrl/ds-guard-xanmod/main/interactive.sh | bash
```

Из учётной записи с sudo:

```bash
curl -fsSL https://raw.githubusercontent.com/ialexisizotov-ctrl/ds-guard-xanmod/main/interactive.sh | sudo --preserve-env=SSH_CONNECTION bash
```

Мастер скачивается целиком и проверяется по закреплённым SHA-256 до запуска.
Комплект rc3 также проверяется отдельно. Постоянных обновлений по расписанию нет.

## Что увидит оператор

1. Русское меню: всё целиком, только XanMod, только Ubuntu, сеть, ds-guard,
   план, состояние, отключение, удаление или отмена прежнего обновления.
2. Проверка совместимости и подготовка ядра рядом с прежним. Повторный запуск
   использует уже скачанные пакеты и проходит те же проверки.
3. Мастер сам определяет точные пункты GRUB и проверяет резервное ядро.
   Основным остаётся текущее работающее ядро.
4. Вопрос: **перезагрузить сейчас / продолжить позже / отменить пробную загрузку**.
   По умолчанию — позже. Без терминала перезагрузка не назначается.
5. После переподключения по SSH запустите **ту же одну команду**. Мастер
   распознает сохранённый этап и продолжит выбранный режим на точном новом ядре.
   Вводить идентификаторы GRUB, выбирать ядро заново или писать команды возврата
   для нормального сценария не требуется.
6. После успешной установки — отдельный вопрос, сделать ли новое ядро основным.
   Прежнее ядро сохраняется. Наличие SSH и локальные проверки не заменяют
   проверку реального клиентского VPN-пути.

Сам установщик не запускается без участия оператора в процессе загрузки ОС.
В этот момент работают только небольшие службы проверки пробного ядра.

## Если новое ядро не подошло

Новое ядро выбирается через `grub-reboot` ровно для одной загрузки. Прежний
`saved_entry` сохраняется. Если Linux дошёл до системных служб, мастер проверяет
службу и порт SSH, адрес интерфейса и прежний маршрут. При подтверждённом
отказе защитная служба запрашивает **один** возвратный перезапуск. Счётчик
записывается на диск до команды перезагрузки, чтобы исключить цикл.

Если ядро зависло **до запуска systemd**, никакой скрипт внутри Linux не сможет
сам себя выполнить. Здесь нужен независимый watchdog хостера/оборудования
либо перезапуск через панель. После такого перезапуска сохранённый выбор GRUB
возвращает прежнее ядро. Именно аппаратный перезапуск предусмотрен и в
[исходном xanmod-migrate](https://github.com/alex72it/xanmod-migrate/blob/main/xanmod-migrate.sh).
Неизвестный watchdog автоматически не включается.

После возврата на прежнее ядро та же команда покажет причину и предложит
закрыть неудачную попытку, посмотреть состояние или выйти. Повторная
установка проблемного ядра автоматически не начинается. После закрытия
попытки открывается обычное меню с новым явным выбором. Если перезапуск
ещё мог быть поставлен в очередь, мастер завершится без новой установки.

Перед пробной загрузкой нужен доступ к консоли/сбросу сервера у хостера.
Работа watchdog и автоматический сброс на конкретном VPS этой программой
не доказаны. Безусловное восстановление после любого зависания не обещается.

Автоматическая проба поддерживает только обычное хранилище GRUB на ext2/ext3/ext4
без LVM, RAID или шифрования под `/boot/grub/grubenv`. Для других вариантов
мастер останавливается до выбора загрузки: возможность погасить разовый выбор
из самого GRUB не считается доказанной одной успешной записью из Linux.

## Совместимость со старым установщиком XanMod

Старая `xanmod-finalize.service` может менять основное ядро самостоятельно.
На время проверки мастер добавляет собственное условие, которое блокирует
её запуск. Чужие unit и скрипт не удаляются и не переписываются.

Если проба отменена или новое ядро не закреплено, при наличии старой службы
эта узкая защита сохраняется: иначе прежняя служба могла бы снова выбрать
непринятое ядро. При явном закреплении нового ядра либо после подтверждённого
удаления его файлов мастер снимает только собственную защиту. Изменённые
другим администратором файлы и параметры GRUB не перезаписываются.

## Состояние, отмена и удаление

В той же команде можно заменить завершающее `bash` на:

```text
bash -s -- --status
bash -s -- --cancel-boot
```

`--status` показывает отдельный журнал мастера. `--cancel-boot` отменяет
принадлежащий мастеру разовый выбор, а после закрепления возвращает прежний
основной пункт. Команда не выгружает работающее ядро и не удаляет пакеты.

Основной журнал: `/var/lib/ds-guard-wizard/boot-trial.json`.
Предыдущие завершённые попытки архивируются. Проверки ядра выполняются
службами `ds-guard-wizard-boot-check` и `ds-guard-wizard-boot-recovery`;
их сообщения доступны через `journalctl -u`.

Отключение, удаление и rollback используют правила rc3. Для старой vendor-установки
без исходного снимка полное удаление всех исторических изменений по-прежнему
недоказуемо и не разрешается. Принудительная выгрузка livepatch и удаление
работающего ядра не выполняются.

## Объём проверки

Результаты новых тестов мастера и отдельной VM фиксируются в
`WIZARD_VALIDATION.json`. Проверки управления загрузкой на лабораторных ядрах
не являются приёмкой XanMod 7.2.9 на каждом production-сервере.
Результаты прежних тестов rc3 и его архив остаются неизменными.
